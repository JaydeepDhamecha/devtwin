01

Is there a local-execution plugin type?

DevTwin reports on a developer's own machine: which runtimes are installed, which ports are listening, whether Postgres or Redis is actually running, Docker state, Git state. That is its entire value.

The dev kit describes plugins as executing server-side over Streamable HTTP. If DevTwin's tools run on MCPHub's server, they will return confident, correct-looking answers about MCPHub's server rather than about the developer's machine. Six of our eighteen tools are affected: devtwin_services, devtwin_drift, devtwin_health, devtwin_check, devtwin_build, devtwin_build_all.

Does MCPHub support a plugin that executes in the caller's local environment — a local runtime, a bridge or agent, or any comparable mechanism?

If yes

We submit all 18 tools. The port is complete and verified against our existing Python server.

If no

We submit only the tools that read repository content and are correct wherever they run — devtwin_detect, devtwin_project_info, devtwin_dependencies, devtwin_precommit — plus the 5 settings tools, and keep the full server on PyPI.

We'd rather ship the smaller honest version than the larger misleading one.

02

Subprocess spawning — will this pass review?

The dev kit lists subprocess spawning as HIGH severity — flagged for review, −15 on the security score. devtwin_check and devtwin_build exist specifically to run a project's own test and build commands, so we can't remove this and still have a product.

What we do to bound it:

  • No tool accepts an arbitrary command. The run parameter selects from commands DevTwin's own adapters discovered in the project; anything else is returned in a rejected list and never executed.
  • Executables are allowlisted — roughly 45 known toolchain binaries. Destructive subcommands (reset, clean, push, rm, prune, --force) are denied even for allowlisted executables.
  • Every command runs through execFile with shell: false and an explicit timeout. There is no path from model-supplied text to a shell string.
  • enableCommandExecution: false disables all three executing tools while the read-only analysis tools keep working.

Is that sufficient to pass review, or is there a sanctioned pattern for plugins that legitimately need to run project commands?

If a reviewer would reject this regardless, we'd rather know now and submit the read-only subset instead of cycling through needs_fixes.

03

Two limits we've engineered around

The 30-second tool execution timeout

Real Gradle and Xcode builds take minutes. We cap every command at platformTimeoutBudgetSeconds (default 25) and report over-budget builds as timed out with timeout_clamped: true, rather than letting them run past the platform limit. Is 25s the right ceiling, and is the budget configurable per plugin or per plan?

The 1MB response limit

Build logs exceed this easily. We truncate per-command output and enforce a serialized ceiling before returning. Confirming the limit is per tool result, not per session.

04

Two fields that are empty by design

getSensitiveConfigFields() returns an empty array

DevTwin authenticates to nothing and stores no credentials — there is deliberately no API key, token, or password in its config schema. Check #4 is vacuously satisfied. Will an empty array pass /mcphub-dev verify, or does the checker expect a non-empty list? We'd rather not add a field that doesn't exist.

dbSchema is unset

DevTwin creates no tables; devtwin_remove has nothing to delete. We read check #16 as non-critical and not applicable here. Please confirm.
